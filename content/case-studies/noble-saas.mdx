## Problem

A solo barber makes $40–60 per cut and does 6–8 cuts a day. They lose 20–30% of that to no-shows — bookings taken by phone, forgotten by the client, and never reminded. Fixing that is not a hard engineering problem. It's a *nobody-can-afford-to-build-it* problem, because the standard tools cost more than the incremental revenue they save.

## Prompt Architecture — Lock what works

The single pattern that made this scale past week two: **once code is verified, it gets locked and named.**

The booking-page slot calculation lives in `src/lib/slots.ts` and `SalonClient.tsx`. It went through 16 rounds of QA in April. Each bug got a name — `BUG-01` through `BUG-15` — and a commit hash. All 16 are documented in `docs/STABLE_LOGIC.md`, which opens with the rule that anchors every Claude session on this repo:

<PromptLog title="docs/STABLE_LOGIC.md — the anti-drift directive">
Do not refactor the functions listed below. Do not "improve" them. Do not restructure them. They handle a specific set of edge cases. If they need to change, add a test first, then change with the test as spec.
</PromptLog>

This is the anti-drift mechanism. Claude, given a codebase without this rule, will helpfully "clean up" a function that survives eight edge cases by removing the special-case handling for two of them. `STABLE_LOGIC.md` is the sign that says *this looks messy for a reason; leave it alone.*

The rest of session context is split across single-purpose files: `CLAUDE.md` (project brief), `CONTEXT_MAP.md` (session restore), `TECH_STACK.md` (versions), `DESIGN_SYSTEM.md` (UI rules), `STRUCTURE.md` (file map). Loading one loads the right slice. No Claude session reads the whole tree.

## Iteration Moment #1 — the April slot-cache freeze

<BeforeAfter>
  <Before date="2026-04-08 → 04-18">

Ten days. 74 commits. A booking page that shipped, worked in dev, worked in staging, and started producing double-bookings within an hour of the first real user. By month's end that number had climbed to 152 — the extra 78 commits were the triage of what shipping fast actually produced.

Every failure mode showed up: race conditions on insert (two people booking the same slot because check-then-insert wasn't atomic). Cache stale between browser refresh and server state. Break windows validated wrong. Timezone drift between the browser calendar and the block-timestamps table. Phone regex too permissive. Email accepting garbage.

  </Before>
  <After date="2026-04-18 16:31 UTC" commit="6b29244">

_"fix: all 16 QA bugs — slot cache, overlap, reschedule, break validation, phone/email validation, timezone UTC"_. 200+ line diff. Each fix numbered. Each numbered fix landed in `STABLE_LOGIC.md`. No refactor allowed after.

  </After>
</BeforeAfter>

**Lesson:** *AI-collaboration velocity is real, and produces exactly the number of bugs you don't test for. 74 commits in 10 days shipped 16 broken edge cases that only showed up under real traffic. QA discipline is the ceiling, not code output.*

## Iteration Moment #2 — Vercel's cache is not your friend

<BeforeAfter>
  <Before date="2026-06-03">

`SalonClient.tsx` fetched bookings client-side on mount. Vercel's Next.js Data Cache — a layer I didn't know was on by default — held Supabase responses for 1–5 minutes. Slots appeared available that had been booked minutes ago. Race conditions returned at scale.

  </Before>
  <After date="2026-06-03 15:09 UTC" commit="d6e1b5a">

_"seed bookedSlotsMap from server on page load, eliminating all client cache issues"_. Plus three sibling commits the same day: bypass Next.js Data Cache on the admin client, force-dynamic on the availability route, sync both `bookedSlotsMap` and `localBookedSlots` after every booking. Server fetches 16 days of bookings via `supabaseAdmin` with `cache: 'no-store'`. Passes as `initialBookings` to the client. Client seeds state immediately. Background refresh continues for freshness. Zero cache layers, top to bottom.

  </After>
</BeforeAfter>

## Reflection

<Pullquote attribution="Lesson from the April sprint">
AI-collaboration velocity is real, and produces exactly the number of bugs you don't test for. QA discipline is the ceiling, not code output.
</Pullquote>

1. **The April sprint proved two things at once.** AI-collab velocity is real — 74 commits in 10 days to live multi-tenant bookings is not a lie. And that velocity produces exactly the number of bugs your QA didn't cover: 16 of them surfaced in production between day 10 and April's end, pushing the month total to 152. The fix isn't slower code; it's a `STABLE_LOGIC.md` that names the bugs after you find them, so the next Claude session doesn't unwind the fixes.

2. **Steady-state isn't done.** Noble hit feature-complete around June. Commit velocity dropped roughly 20× in daily terms — ~7 commits/day during the April sprint to ~0.3 commits/day in steady state (6–11/month). But the project isn't paused; it moved layers. Claude now writes marketing content, not code. The interesting work migrated from "build the app" to "build the machine that grows the app." That reallocation is what AI-first solo work makes possible — a traditional team wouldn't reslot this cleanly.

3. **The most valuable file in this repo is `docs/STABLE_LOGIC.md`, not the code.** It's 170 lines. It documents the exact functions that survived edge cases and forbids future refactors. Anything I ship after this will have one — before the first bug fix, not after the tenth.
