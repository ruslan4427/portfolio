## Context

Angel Trucking is a real ~100-truck carrier in Ohio. ~150 people touch the system: 1–2 admins, 3–5 managers, 5–10 mechanics, 50–70 drivers, plus candidates and the public marketplace. This is the only client project in my portfolio — the rest are personal.

## Problem

Every existing trucking SaaS handles one slice: TMS, or maintenance, or hiring. None cover all four *and* work on a phone in a cab with no signal. Screening drivers manually is slow. Booking shop time by phone is chaos. Marketplace listings never get to Facebook. The client didn't need better software for one problem — they needed one system for four.

## Prompt Architecture — the 5-stage pipeline

Every task passes through **five roles**, in order: Orchestrator → PM → Designer → Developer → Reviewer. Each role has its own `AGENTS.md`-declared contract.

<PromptLog title="AGENTS.md — the 5-role contract">
The PM asks up to 5 clarifying questions and then writes a Task Brief. The Designer never codes. The Developer never re-designs. The Reviewer validates against three docs: Brief, Design Spec, V9 tokens.
</PromptLog>

The rule that keeps sessions sharp: **"Spec + one file, not the codebase."** Claude never reads the whole tree — every task hands it the Brief and the specific files by name. This is what stops mid-session context rot.

## Iteration Moment

Only one commit exists (`b652cd3`, 2026-05-12) — the entire agent architecture and 4-sprint roadmap were built *before* production code. That's the pivot: instead of jumping into features and refactoring later, I front-loaded the agent design. All four sprints (auth, HR, marketplace, shop + fleet) have since been built in the working tree against that scaffold; what remains is the client deployment and the first live users. **Lesson: for a 4-module product, an hour designing the pipeline saves a week of rewrites.**

## Reflection

1. **Multi-stage prompts scale where single prompts collapse.** By Sprint 3, one-prompt "just build the shop module" would have produced slop. Five-stage forced explicit design decisions before code.
2. **Business rules belong in code, not docs.** The 3-year speeding rule lives in `lib/ai/screening.ts`, not a policy PDF. If the rule changes, one file changes.
3. **The most valuable file in the repo is `AGENTS.md`, not the code.** Anyone reading it can predict how the next feature will get built.
